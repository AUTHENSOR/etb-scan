# The Evaluator Trust Boundary: ETB-01 through ETB-10

## The name

**Evaluator Trust Boundary (ETB) failure.**

> An evaluator commits an ETB failure when its score depends on an artifact the evaluated system can influence.

The narrower label "verdict injection" names only ETB-01. Nine of the ten classes involve no injection at all: dropped denominators, fail-open error paths, and forged execution artifacts are trust-boundary violations with no attacker string anywhere.

## The invariant

Every class below is one violation seen from a different angle:

> **A score must be a function only of state the evaluated system cannot reach.**

Where an evaluator reads model-controlled text as a verdict, treats a missing measurement as a passing one, or trusts a self-reported execution result, it has moved the trust boundary inside the thing it is measuring.

## The ten classes

| ID | Failure | Mechanism | Fix pattern |
|---|---|---|---|
| **ETB-01** | Injected verdict trusted | The judge extracts a score from model-controlled text (greedy first-match JSON or regex over the candidate answer) | Parse the judge's own structured verdict; bind extraction to the last or explicitly delimited block; never read the candidate |
| **ETB-02** | Unsanitized model output in the evaluator prompt | Model text (answers, CoT, tool arguments, transcripts) flows unescaped into the judge or monitor prompt | Escape or structurally neutralize model output before it enters any grader prompt; use message-role separation |
| **ETB-03** | Fail-open on error | A backend, parse, or vendor error is coerced to "safe" or "pass" | Fail closed; flag the sample; never default to safe |
| **ETB-04** | Denominator drop | Unscorable, refused, or errored samples are silently excluded from the mean, inflating the score | Count them, or surface them as a separate reported quantity |
| **ETB-05** | Unscorable read as behavior-absent | "Could not score" is conflated with "the attack did not succeed" | Distinguish could-not-score from safe at the type level |
| **ETB-06** | Missing normalization | Homoglyph, zero-width, or Unicode-steganographic content evades a detector | Normalize both trigger strings and model output before matching |
| **ETB-07** | Composition blindness | Per-step monitors miss an attack distributed across individually benign steps | Carry cross-step state in the monitor |
| **ETB-08** | Metric miscounting | Whole-dict positivity, multi-answer under-count, name-collision collapse | Per-key and per-answer scoring |
| **ETB-09** | Forged execution artifact | A runner trusts a self-reported `PASSED`, an always-equal return, or spoofed stdout | Verify against frozen ground truth the policy cannot influence |
| **ETB-10** | Evaluation context leakage | Environment variables, run identifiers, or harness artifacts let the agent detect it is being evaluated and condition on it | Strip or randomize identifying context; treat detectability as a measured property |

## Evidential weight is uneven, and two classes are thin

Eight of the ten classes rest on four or more independent instances: ETB-01, 02, 03, 04, 05, 06, 08 and 09.

**ETB-07 and ETB-10 each rest on a single observation.** Both are included because each is named as a distinct failure mode in the phase-1 audit and each has a clear fix pattern, but a single instance is a hypothesis about a class, not a measurement of one. Weight them accordingly.

Per-class instance counts are not recorded on this page. They are generated by `paper/classify.py` into [EVIDENCE-TABLE.md](EVIDENCE-TABLE.md) from the raw report data, so there is one place to be wrong and it is not this one.

## ETB-07 is the control case, not the exception

ETB-07 is the one class with a maintainer on record calling the behavior intentional. On `UKGovernmentBEIS/control-arena#792` the maintainer replied that the default per-step prompt formatter is deliberately cheap and stateless, and that cross-step state is a configuration choice.

That response is correct on its own terms. It is also the most informative single data point in the sample, because **ETB-07 is the one place where the trust boundary was already present in a maintainer's model of their own code.** They could see it, so they reasoned about it explicitly, priced the cost, and chose where to put it. Elsewhere the boundary was not visible at all.

That makes ETB-07 the counterfactual that supports the invisibility reading rather than a counterexample to it. Where maintainers can see the boundary they make deliberate, defensible tradeoffs. The other nine classes are not worse engineering. They are the same engineers working without the concept.

**The finding here is a disclosure gap, not a code defect.** A search of the `control-arena` repository returns no matches for `cross-step` or `composition`, so the tradeoff is known to maintainers but is not surfaced anywhere a consumer of the eval results would encounter it. Someone reading monitor output has no way to learn that attacks distributed across individually benign steps pass by design.

The claim is therefore narrow: this is a deliberate, cost-motivated open tradeoff that is not documented for the people consuming the numbers. It is not a vulnerability, and it is classified here as an undocumented tradeoff rather than as a defect.

## Identifier discipline

- IDs are permanent. Once ETB-0n is published it is never reassigned.
- Each class has a stable anchor URL at <https://www.authensor.com/etb>, because the value of the schema is that other people's issue trackers and vendor questionnaires can cite it.
- New classes append (ETB-11, ETB-12). The ten above do not renumber.
